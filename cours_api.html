Chapitre 1

C'est quoi une API, au juste ?

API veut dire Application Programming Interface — « interface de programmation ». Derrière ce nom un peu froid se cache une idée très simple : c'est un intermédiaire qui permet à deux programmes de se parler, sans que l'un ait besoin de connaître le fonctionnement interne de l'autre.

L'image Le serveur au restaurant. Tu ne vas pas en cuisine préparer ton plat. Tu lis un menu, tu passes commande à un serveur, il revient avec l'assiette. Tu ignores totalement comment la cuisine fonctionne — et c'est très bien. L'API, c'est ce serveur : un intermédiaire avec un menu de demandes possibles.

Une API définit donc deux choses : ce qu'on peut demander (le menu) et sous quelle forme on reçoit la réponse. Tant que ces deux points ne changent pas, la cuisine peut être réorganisée sans que le client ne s'en aperçoive.

?

Pourquoi ne pas tout mettre au même endroit ?

Parce que séparer les rôles rend chaque partie plus simple, plus sûre et remplaçable. Le dashboard s'occupe d'afficher, l'API s'occupe d'aller chercher les données. Chacun son métier.

◆ Dans ton projet

Ton tableau de bord (Streamlit) ne sait pas parler à la base de données BigQuery, et c'est voulu. Il passe par ton API, qui joue le serveur : « donne-moi le nombre d'offres par région » → l'API va chercher, revient avec la réponse. Le dashboard n'a jamais mis les pieds « en cuisine ».

Chapitre 2

Client et serveur : qui parle à qui

Toute communication via API repose sur deux rôles. Le client est celui qui demande. Le serveur est celui qui répond. Le client envoie une requête (request), le serveur renvoie une réponse (response). C'est toujours le client qui initie — le serveur ne parle jamais en premier.

L'image Un coup de téléphone. C'est toi qui appelles (client). L'interlocuteur décroche et répond (serveur). Il ne t'appelle pas spontanément pour te donner l'heure — tu dois demander.

Un même programme peut être client dans une relation et serveur dans une autre. C'est exactement le cas de ton API.

◆ Dans ton projet

Ton API est à la fois serveur (elle répond à Streamlit) et cliente (elle demande des données à BigQuery). Elle est au milieu de la chaîne :

Streamlit  →demande→  API  →demande→  BigQuery
 (client)              (serveur     (serveur)
                        ET client)

Chapitre 3

HTTP : le langage commun du web

Pour que client et serveur se comprennent, il leur faut une langue commune. Sur le web, cette langue s'appelle HTTP (HyperText Transfer Protocol). C'est un ensemble de règles qui décrivent comment formuler une requête et une réponse. Chaque fois que tu ouvres une page web, ton navigateur parle HTTP sans que tu le saches.

Le S de HTTPS ajoute juste le chiffrement (la communication est sécurisée). Le principe reste identique.

✓

L'essentiel

HTTP est un protocole requête → réponse. Une requête part, une réponse revient, et la conversation est terminée. Pour une nouvelle information, on refait une requête. Le serveur ne « se souvient » de rien entre deux appels (on dit qu'il est sans état, stateless).

◆ Dans ton projet

Quand ton dashboard affiche la carte des régions, il envoie une requête HTTP à ton API. Quand tu changes un filtre, il en renvoie une nouvelle. Chaque graphique = une ou plusieurs requêtes HTTP.

Chapitre 4

L'anatomie d'une requête

Une requête HTTP est composée de quelques éléments. Décortiquons une vraie requête de ton projet :

GET http://localhost:8000/api/geo/regions?metier=Data+Engineer
▲ méthode     ▲ adresse (URL)     ▲ paramètres

On y trouve :

ÉlémentRôleDans l'exemple
MéthodeL'action voulueGET = « donne-moi »
URLL'adresse de la ressource.../api/geo/regions
ParamètresDes précisions sur la demande?metier=Data Engineer
En-têtes (headers)Métadonnées (format attendu, authentification…)gérés automatiquement

La réponse a une structure symétrique : un code de statut (a-t-on réussi ?), des en-têtes, et un corps (la donnée demandée). On voit ça aux chapitres 6 et 7.

Chapitre 5

Les méthodes HTTP : le verbe de la demande

La méthode dit quelle action on veut effectuer. Il en existe plusieurs, mais quatre couvrent l'essentiel — on les résume souvent par l'acronyme CRUD (Create, Read, Update, Delete) :

MéthodeIntentionAnalogie restaurant
GETLire une donnée (sans rien modifier)Consulter le menu
POSTCréer / envoyer une donnéePasser une commande
PUTMettre à jour une donnée existanteModifier sa commande
DELETESupprimer une donnéeAnnuler sa commande
✓

La distinction clé : lire vs modifier

GET ne change jamais rien côté serveur — on peut le rejouer mille fois sans effet. POST agit (il crée quelque chose). Cette différence guide le choix de la méthode.

◆ Dans ton projet

Ton dashboard ne fait que consulter des données pour les afficher : la quasi-totalité de tes endpoints sont donc en GET. La seule exception prévue est la recommandation par CV, en POST : là, on envoie le contenu d'un CV à l'API pour qu'elle calcule des correspondances — on transmet une donnée, d'où le POST.

Chapitre 6

Les codes de statut : « ça s'est bien passé ? »

Chaque réponse HTTP commence par un nombre à trois chiffres qui résume le résultat. Le premier chiffre donne la grande famille :

2xxSuccès. Le plus courant : 200 OK. Tout s'est bien passé, la réponse contient la donnée.
4xxErreur du client. La demande est fautive. 404 Not Found (adresse inexistante), 422 (paramètre invalide).
5xxErreur du serveur. La demande était correcte mais le serveur a planté. 500 (erreur interne), 503 (service indisponible).
L'image 4xx vs 5xx : un 4xx, c'est « tu as mal commandé » (plat qui n'existe pas au menu). Un 5xx, c'est « la cuisine a pris feu » — ta commande était valable, mais le problème vient de l'autre côté.
◆ Dans ton projet

Tu as rencontré ces codes en vrai ! Le 500 quand l'authentification BigQuery manquait (le serveur plantait), et le 404 sur la recommandation (la route n'existe pas encore). Ton API transforme d'ailleurs proprement une panne BigQuery en 503 avec un message clair, au lieu d'un 500 brut — c'est une bonne pratique de gestion d'erreurs.

Chapitre 7

JSON : le format d'échange

Client et serveur doivent échanger des données dans un format que les deux comprennent. Le standard du web s'appelle JSON (JavaScript Object Notation). C'est du texte structuré, lisible par un humain comme par une machine.

JSON repose sur deux briques : les objets (des paires clé-valeur, entre { }) et les listes (des séries de valeurs, entre [ ]). Exemple tiré de ton API :

// un objet : les chiffres clés (réponse de /api/kpis/overview)
{
  "nb_offres": 723,
  "nb_entreprises": 412,
  "nb_metiers": 13,
  "nb_regions": 18
}

// une liste d'objets : offres par région (/api/geo/regions)
[
  { "label": "Île-de-France", "nb_offres": 87 },
  { "label": "Occitanie",     "nb_offres": 21 }
]
✓

Pourquoi JSON et pas un tableau Excel ?

Parce que JSON est universel : tout langage de programmation sait le lire et l'écrire. Ton API le produit en Python, ton dashboard le relit en Python, mais une appli mobile en Java ou un site en JavaScript pourraient consommer exactement le même JSON.

Chapitre 8

REST : une façon d'organiser une API

Jusqu'ici on a vu les briques (HTTP, méthodes, JSON). REST est un style d'architecture : une manière conventionnelle de les assembler pour construire une API claire et prévisible. Une API qui suit ces conventions est dite « RESTful ».

Les principes principaux de REST :

PrincipeCe que ça veut dire
Ressources identifiées par des URLChaque type de donnée a sa propre adresse : /regions, /metiers…
Les méthodes portent l'actionC'est GET/POST qui disent quoi faire, pas l'URL.
Sans état (stateless)Chaque requête est autonome, le serveur ne mémorise rien entre deux appels.
Réponses structuréesGénéralement du JSON + un code de statut.
!

Un bon nommage d'URL est un nom, pas un verbe

On écrit GET /api/geo/regions (la ressource « régions »), pas /getRegions. Le verbe est déjà porté par la méthode GET. C'est une convention REST qui rend l'API lisible.

◆ Dans ton projet

Ton API est RESTful : des URL qui nomment des ressources (/api/kpis/overview, /api/competences/repartition), tout en GET pour la lecture, des réponses en JSON. C'est ce qui la rend simple à parcourir et à documenter.

Chapitre 9

Endpoints et paramètres

Un endpoint (« point de terminaison ») est une URL précise que l'API sait traiter. C'est un « plat » du menu. Ton API en expose une dizaine, regroupés par thème.

Les query parameters : préciser la demande

Après le ? dans une URL, on ajoute des query parameters — des précisions optionnelles. Ils s'écrivent clé=valeur, séparés par & :

/api/geo/regions?metier=Data+Engineer&type_contrat=CDI

Ici on demande les offres par région, mais uniquement pour le métier Data Engineer et en CDI. Ce sont tes filtres.

◆ Dans ton projet

Tu as fait un choix élégant : tous tes endpoints acceptent le même jeu de filtres (région, métier, contrat, période…). Résultat : la barre latérale du dashboard pilote toutes les pages de la même façon. Voici le menu complet de ton API :

Chapitre 10

FastAPI : l'outil qui construit l'API

Tout ce qu'on a vu, il faut un outil pour le mettre en œuvre en Python. Ton projet utilise FastAPI : un framework (une boîte à outils) moderne pour construire des API. On lui a préféré ses concurrents pour trois raisons : il est rapide, il valide les données automatiquement, et il génère sa propre documentation.

Un endpoint FastAPI, décortiqué

Voici un vrai endpoint de ton projet, ligne par ligne :

@router.get("/overview", response_model=KpiOverview)
def read_kpi_overview(filters: FilterParams = Depends(get_filters)):
    return kpis_service.get_kpi_overview(filters)
Bout de codeTraduction
@router.get("/overview")« Quand on reçoit un GET sur cette URL, exécute la fonction dessous. »
response_model=KpiOverview« La réponse aura obligatoirement cette forme. » (voir chap. 11)
Depends(get_filters)« Récupère d'abord les filtres de l'URL, puis passe-les à la fonction. »
return ...service...« Délègue le vrai travail (le SQL) à la couche service. »
✓

La documentation gratuite

En lançant ton API, ouvre http://localhost:8000/docs. FastAPI y génère tout seul une page interactive listant tes endpoints, leurs paramètres, et permettant de les tester en direct. Tu n'as rien écrit pour ça — c'est un cadeau du framework, et l'outil idéal pour ta soutenance.

Le rôle de Depends : ne pas se répéter

Tes 13 endpoints acceptent les mêmes filtres. Plutôt que de recopier 13 fois la liste des paramètres, tu l'as définie une seule fois dans get_filters, et chaque endpoint la « réclame » via Depends(). FastAPI se charge de lire l'URL et de fabriquer l'objet FilterParams avant d'appeler ta fonction. C'est le principe d'injection de dépendance : la fonction déclare ce dont elle a besoin, le framework le fournit.

Chapitre 11

Pydantic : garantir la forme des données

Pydantic est la bibliothèque qui, dans FastAPI, décrit et vérifie la forme des données. On définit une classe qui liste les champs attendus et leur type ; Pydantic garantit ensuite que rien d'autre ne passe.

# schemas/kpis.py — le contrat de la réponse "chiffres clés"
class KpiOverview(BaseModel):
    nb_offres: int
    nb_entreprises: int
    nb_metiers: int
    salaire_min_moyen: float | None = None

Cette classe dit : « une réponse KpiOverview a un nb_offres qui est un entier, … et un salaire_min_moyen qui est un décimal ou peut être absent (None) ». Si le code tentait de renvoyer du texte dans nb_offres, Pydantic bloquerait immédiatement, côté serveur.

!

Un contrat qui protège les deux côtés

Le dashboard peut faire confiance à la forme de la réponse : elle est garantie. Et si un jour le SQL renvoie une donnée mal typée, l'erreur est attrapée à la source plutôt que de provoquer un bug obscur à l'affichage. C'est un filet de sécurité.

◆ Dans ton projet

Chaque famille de réponse a son modèle Pydantic : KpiOverview, RepartitionItem (pour les listes label/nb_offres), SalaireMetier… C'est aussi pour ça qu'on a dû gérer le cas où les compétences renvoient competence au lieu de label : chaque contrat est distinct, et le dashboard doit lire la bonne clé.

Chapitre 13

Visite guidée du dossier api/

Maintenant que les notions sont en place, ouvrons le capot. Chaque fichier de ton API a un rôle précis, et leur organisation n'est pas arbitraire : elle applique le principe de séparation des responsabilités vu au chapitre 10. Voici la carte complète.

# Arborescence du dossier api/ — l'organisation en couches
api/
├── main.py            # le chef d'orchestre : démarre l'appli
├── dependencies.py     # les filtres partagés par tous les endpoints
│
├── core/
│   └── config.py       # la configuration (projet, dataset…)
│
├── db/
│   └── bigquery.py     # la connexion et l'exécution des requêtes
│
├── routes/             # LES URL — quoi répondre, à quelle adresse
│   ├── kpis.py
│   ├── geo.py
│   ├── metiers.py
│   ├── competences.py
│   ├── secteurs.py
│   ├── contrats.py
│   ├── profil.py
│   ├── insights.py
│   └── offres.py
│
├── services/           # LA LOGIQUE — construire le SQL, parler à la base
│   ├── base.py         # les jointures communes (le socle SQL)
│   ├── kpis.py
│   ├── geo.py          # … un fichier par domaine, en miroir de routes/
│   └── …
│
└── schemas/            # LES CONTRATS — la forme garantie des réponses
    ├── common.py       # modèles réutilisés (RepartitionItem…)
    ├── kpis.py
    └── …

Le trio qui structure tout : routes / services / schemas

C'est l'idée centrale à retenir. Pour un même domaine (les métiers, la géo…), le travail est réparti en trois fichiers portant le même nom, dans trois dossiers différents :

DossierRépond à la questionContient
routes/À quelle URL, et quels paramètres ?Les endpoints. Aucune logique métier.
services/Comment obtenir la donnée ?La construction du SQL, l'appel à BigQuery.
schemas/Quelle forme aura la réponse ?Les modèles Pydantic.
L'image La brigade de cuisine. routes/ est le serveur qui prend la commande, services/ est le cuisinier qui la prépare, schemas/ est le dressage imposé de l'assiette. Chacun son poste — si le cuisinier change sa recette, le serveur n'a rien à changer.
!

Pourquoi un fichier par domaine plutôt qu'un seul gros fichier ?

Parce qu'on s'y retrouve. Pour modifier les compétences, tu ouvres routes/competences.py et services/competences.py — tu sais exactement où chercher. Un fichier unique de 1000 lignes serait un cauchemar à maintenir et impossible à travailler à plusieurs.

Les fichiers « transversaux »

Quatre fichiers ne concernent pas un domaine précis mais servent tout le monde :

FichierRôle détaillé
main.py Le point d'entrée. Il crée l'application FastAPI, y branche tous les routers (les fichiers de routes/), configure les autorisations d'accès (CORS pour que Streamlit puisse l'appeler) et gère les erreurs globales (la panne BigQuery → 503). C'est le fichier qu'uvicorn lance.
dependencies.py Définit FilterParams et get_filters : le jeu de filtres commun injecté partout via Depends (chap. 10). Contient aussi la logique qui transforme un filtre en condition SQL paramétrée sécurisée.
core/config.py Lit la configuration depuis le .env (BQ_PROJECT_ID, BQ_DATASET). Aucun secret en dur. C'est ici qu'on résolvait ton erreur de démarrage.
db/bigquery.py Crée le client BigQuery (une seule fois, partagé) et expose run_query() : la fonction unique par laquelle passent toutes les requêtes SQL, avec la gestion d'erreurs centralisée.
✓

Et les __init__.py vides ?

Ces petits fichiers (souvent vides) signalent simplement à Python que le dossier est un « package » importable. C'est ce qui permet d'écrire from api.services import geo. Purement technique, rien à comprendre de plus.

Le cas de services/base.py

Un fichier de service à part : il ne traite aucun domaine, il fournit le socle SQL commun. Comme presque toutes tes requêtes joignent fact_offres à ses dimensions (métier, région, date…), cette jointure est écrite une seule fois ici et réutilisée par tous les autres services. Éviter la répétition, encore.

◆ Le trajet d'un fichier à l'autre

Reprenons l'appel /api/geo/regions. Il traverse tes fichiers dans cet ordre précis :

# 1 main.py          # a branché le router "geo" au démarrage
# 2 routes/geo.py     # reçoit l'URL + Depends(get_filters)
# 3 dependencies.py   # fournit les filtres validés
# 4 services/geo.py   # construit le SQL…
# 5 services/base.py  # …avec les jointures communes
# 6 db/bigquery.py    # exécute contre BigQuery
# 7 schemas/common.py # valide la forme (RepartitionItem)
    ↩ la réponse JSON repart vers Streamlit

À retenir sur l'organisation

  • routes / services / schemas — le même domaine réparti en 3 rôles : URL, logique, forme.
  • Un fichier par domaine — on sait toujours où chercher ; travail à plusieurs facilité.
  • main.py — le chef d'orchestre qui assemble tout au démarrage.
  • dependencies / config / bigquery — les briques transversales partagées.
  • base.py — le socle SQL commun, écrit une fois, réutilisé partout.
